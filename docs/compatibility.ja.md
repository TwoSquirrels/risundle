# risundle が対応できるライブラリの条件

C++ の `#include` は単なるテキスト展開であり、ファイルをどう分割していてもコンパイルさえ通れば有効である。しかし risundle はライブラリの各ファイルを個別に解析して要不要を判定するため、この自由な分割の全てには対応できない。ある程度行儀の良い分割をしているライブラリだけが対象になる。

「行儀の良い」の正確な境界、つまりツールが正しく動く必要十分条件を過不足なく述べるのは難しい。そこで本書では、それに近い十分条件 — これを満たしていれば壊れない、という書き方 — を示す。

先に安心材料を述べると、各ファイルが自分の名前空間を自分で開いて閉じ、名前の付いた定義を素直に書いてある、ごく普通のヘッダーオンリーライブラリなら、以下の条件は何もせずに満たしている。AC Library をはじめ、主要な競プロライブラリはこの形である。

また、この条件が問われるのは展開される (維持指定しない) ライブラリだけである。維持指定 (keep) したライブラリは展開も tree-shaking もされず `#include` のまま残るため、条件を満たさないライブラリでも、ジャッジ側に存在するなら維持指定して使う分には問題ない。ライブラリの登録や維持指定の操作は [README](../README.ja.md) を参照。

## 大前提: risundle は削るだけで、足すことはしない

バンドルは「元の解答をそのまま展開し、不要なヘッダーを削る」処理であり、足りないものを risundle が探して補うことはない。したがって**バンドル前の解答が、ライブラリの場所を `-I` で伝えればそのままコンパイル・リンクの通る状態であること**が全ての前提になる。元が通らない解答は、バンドルしても通らない。なお、バンドルできる解答は 1 つのソースファイルだけで、複数の .cpp を一緒にバンドルすることはできない (解答をヘッダーに分割して include する構成はソースが 1 つなのでこの制限には当たらないが、後述の「ライブラリを使うコードは、解答ファイル本体に書くこと」に注意)。

この前提から導かれる、踏みやすい落とし穴が 1 つある。宣言と実装が別ファイルに分かれたライブラリでは、**実装ファイルも解答側で include されていなければならない**。宣言ヘッダーだけを include した解答に対して、risundle が実装ファイルを察して足すことはない (これは元の解答がリンクエラーになる状態であり、前提から外れている)。シンボルの到達性から実装ファイルを自動で取り込む構想は [#10](https://github.com/TwoSquirrels/risundle/issues/10) にあるが、当面は予定していない。

## 各ファイルは、それ単独で完結した C++ の宣言であること

risundle は `library add` の時点で、ライブラリの各ファイルをプリプロセスせず個別に構文解析し、そのファイルが定義する名前 (クラス・関数・変数など) を記録する。バンドル時は、解答に現れる名前からこの記録を逆引きして、必要なファイルだけを残す。つまり各ファイルには、次の 2 つが求められる。

- **それ単独で構文解析できること。** ファイルが開いたスコープ (`{`・`namespace` など) は同じファイル内で閉じ、他のファイルが開いたスコープの続きから書き始めない。
- **自分が残るべき手がかりを、名前として持っていること。** 名前の付いた定義か、クラス外実装 (実装先の型名が拾われる。[spec.ja.md](spec.ja.md) の「実装ファイルの維持」を参照) のどちらかを含む。どちらも持たないファイルは「使われていない」としか判定できず、tree-shaking で消え得る。

この条件が崩れる典型的な書き方を挙げる。

### スコープの開閉がファイルを跨いでいる

次のように関数の途中でファイルを割ると、`back.hpp` は名前を何も持たないため削除され、`front.hpp` の開き括弧が閉じないままコンパイルエラーになる。

```cpp
// front.hpp
int solve() {

// back.hpp
  return 42;
}
```

名前空間を別ファイルの `#include` に被せる書き方も同じ理由で壊れる。

```cpp
// wrapper.hpp
namespace mylib {
#include "impl.hpp"
}

// impl.hpp
struct Vector {};
```

`wrapper.hpp` 自身は名前を持たないため丸ごと削除され、`impl.hpp` の中身が `namespace mylib` を伴わずグローバルスコープへ出力される。解答が `mylib::Vector` と修飾していればコンパイルエラーで気づけるが、`using namespace mylib;` などで修飾せずに使っていると、名前の意味が変わったまま黙ってコンパイルが通る恐れがある。

### マクロで宣言の名前を生成している

登録時の解析はプリプロセスをしないため、マクロの展開結果ではなくソースの字面を見る。マクロで型名や関数名を生成する構成 (いわゆる X-macro) では、生成される名前が一切記録されない。

```cpp
#define DEFINE_POINT(Name) struct Name { int x, y; };
DEFINE_POINT(Point)
```

このファイルを登録しても `Point` はどこにも記録されず、解答が `Point` を使っていてもファイルの必要性を判定できないため、削除されてしまう。

どうしてもマクロで名前を生成したい場合は、生成される名前を素の前方宣言としても同じファイルに書いておけばよい。

```cpp
#define DEFINE_POINT(Name) struct Name { int x, y; };
DEFINE_POINT(Point)
struct Point;
```

前方宣言は字面のまま構文解析できるため `Point` が記録され、ファイルが維持されるようになる。宣言の重複は C++ 的に無害なので、ライブラリの動作は変わらない。クラスに限らず、関数 (`int f(int);`) や変数 (`extern int x;`) の宣言でも同じように機能する。

なお `#ifdef` によるプラットフォーム分岐は、プリプロセスしないことがむしろ利点として働く。各分岐がそれぞれ完結した宣言になっていれば、どちらが選ばれるかに関わらず両方の名前が安全側に記録される。

### 壊れたときの見え方

この条件に反してファイルが消えたときの現れ方は、ほとんどの場合コンパイルエラーかリンクエラーである。

- 構文自体が壊れる場合 (関数分割の例) や、使っている定義そのものが失われる場合 (X-macro の例) は、コンパイルエラーになる。
- 宣言はクラス側に残ったまま実装だけが欠落する場合 (実装先を静的に特定できない実装ファイル。自由関数の演算子だけを定義するファイルなど) は、リンクエラー (undefined reference) になる。記号演算子は名前を持たないため、この種のファイルは前方宣言では救えない。

唯一の例外は名前空間ラッパーの例で、解答が修飾せずに使っていると、エラーにならないまま黙って意味が変わり得る。

なお、クラス外実装や明示的特殊化が手がかりとして働くのは、実装先の型 (主テンプレート) が登録済みライブラリの展開されるファイルで定義されている場合に限る。実装先がライブラリの外にあるファイル — たとえば `std::hash` の特殊化だけを置いたファイル — も同じように消え得るが、こちらは特殊化ごと失われるため、リンクエラーではなくコンパイルエラーとして現れる。

コンパイル・リンクエラーは、提出前に手元で検証すれば気づける。手順は [cheatsheet.ja.md](cheatsheet.ja.md) の自動フォールバック (バンドル後を手元でコンパイルし、失敗したら全展開へ切り替えるシェルの組み方) の項を参照。恒久的な対処はライブラリ側の構成変更で、たとえば演算子の定義は名前の付いた定義と同じファイル (またはクラス本体のファイル) に置けば維持される。急場は `--no-tree-shaking` でしのげる。

## ライブラリを使うコードは、解答ファイル本体に書くこと

バンドル時に「解答が何を使っているか」を調べる対象は、解答ファイル自身に書かれた行に限られる。登録していない自作のローカルヘッダーの中でだけライブラリを使うと、その依存は検出されず誤って削除され得る。ローカルヘッダー自体は tree-shaking の対象外なので展開されて丸ごと残るが、その中で使われているライブラリヘッダーの方が消える。この問題は [#60](https://github.com/TwoSquirrels/risundle/issues/60) で追跡しており、設計上の限界ではなく修正され得る。

## tree-shaking の単位はファイルである

要不要の判定は行やメンバの単位ではなく、ファイル (ヘッダー) 単位で行う。1 つのファイルに使う定義と使わない定義が混在していても、そのファイルは丸ごと残る。出力をさらに小さくしたければ、ライブラリのファイル分割を細かくするほど tree-shaking はよく効く。

## その他の注意点

- **`library` という名前のファイルは、そのままではバンドルできない。** 先頭引数の `library` は常にライブラリ管理サブコマンドとして解釈されるため、`risundle ./library` のようにパスとして明示する。
- **維持指定 (keep) したライブラリは `<>` 形式で include する。** `#include "..."` で書き、かつ解答ファイルと同じディレクトリに同名パス (例: `./atcoder/dsu`) が偶然存在すると、`""` がカレントディレクトリを先に探すという、コンパイラからは抑制できない C++ 標準の動作によってそちらが使われ、維持指定が効かずライブラリが展開されてしまう。

## 本書に書いていないこと

本書の条件は、名前を記録して逆引きするという仕組みに由来する設計上の限界であり、修正の予定はない (修正され得ると明記した [#60](https://github.com/TwoSquirrels/risundle/issues/60) を除く)。これとは別に修正予定の既知のバグもあるが、いずれ直るものなので本書では列挙しない。[`Kind/Bug`](https://github.com/TwoSquirrels/risundle/issues?q=is%3Aissue+state%3Aopen+label%3AKind%2FBug) ラベルを参照。
